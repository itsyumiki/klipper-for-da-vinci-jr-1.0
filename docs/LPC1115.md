# Klipper on the LPC1115 (NXP LPC11xx, Cortex-M0)

This is a generic Klipper MCU port for the NXP LPC1115 (and, with minor
differences, the other LPC111x parts). It lives in `src/lpc1115/` and is
selected with `Micro-controller Architecture = LPC1115 (Cortex-M0)` in
`make menuconfig`.

The port is deliberately generic: it contains no board-specific pins,
defaults or safety logic. Board specifics belong in `printer.cfg`.

## Status

| Area | State |
|---|---|
| Scheduler timer, command layer, UART protocol | works on hardware |
| Digital GPIO (`output_pin`, blink demo) | recorded as working with the early GPIO-only build; with the 256-byte stack, any config with a move-queue object followed by `finalize_config` hard-faulted (see [LPC1115-finalize-hardfault.md](LPC1115-finalize-hardfault.md)). Fix (1 KiB stack) is in the tree and passed a first console test on hardware (digital out + `finalize_config` on `PIO2_10`, MCU stayed up); broader testing (`PIO0_9`, soak, real Klippy `output_pin`) still to do |
| Klippy integration | runs as a secondary MCU (`mcu lpc1115`, load 0.07 at 12 MHz); a hotend output pin, thermistor ADC input, heater and hotend fan registered and working (owner report, 2026-10-26) |
| Reset (`FIRMWARE_RESTART`/`RESTART`) | builds, not yet tested on hardware |
| Watchdog | observed to reset a hung MCU about 0.5 s later (`starting`); no long soak run yet |
| ADC | reads plausible values (hotend NTC about 23-24 degC, owner observation, not compared to a reference) |
| Hardware PWM | builds, not yet tested on hardware |
| SPI (SSP0/SSP1) | builds, not yet tested on hardware |
| I2C | builds, not yet tested on hardware |
| PLL / faster clock | not implemented (runs at 12 MHz) |
| USB, CAN, UART1-style extra serial, bootloader request | not implemented |

"Builds" means it compiles without warnings and the firmware dictionary
contains the expected commands. It does not mean the peripheral has been
exercised.

## Building

    cp test/configs/lpc1115.config .config
    make olddefconfig
    make -j2

Or run `make menuconfig` and select the LPC1115 architecture. The result is
`out/klipper.bin` (about 42 KB of the 64 KB flash, about 0.86 KB static RAM).

Build notes:

* `klipper.bin` is post-processed by `scripts/lpc11xx_checksum.py`, which
  writes the boot ROM checksum into vector table word 7 (the LPC11xx boot
  ROM only starts an image whose first eight vector words sum to zero).
  The script also refuses to emit an image with a code-read-protection
  (CRP) value that would lock out ISP/SWD.
* The linker script reserves the CRP word at flash offset `0x2FC` and sets
  it to `0xFFFFFFFF` (no protection). Normal code starts at `0x300`.
* Always flash `out/klipper.bin`, not the `.elf`, because only the `.bin`
  has the checksum.

## Flashing

The image is flashed at address `0x0` through the chip's ROM ISP UART or SWD.
Keep an SWD recovery path available before the first flash. This repository
does not prescribe a flashing tool. Any tool that can write a raw binary to
flash address 0 on an LPC11xx works.

## Hardware resources

| Resource | Value |
|---|---|
| Clock | 12 MHz internal RC oscillator, no PLL (`CLOCK_FREQ` = 12000000) |
| Flash / RAM | 64 KiB at 0x0 / 8 KiB at 0x10000000 |
| RAM used by Klipper | `RAM_SIZE` is 0x1fe0 (top 32 bytes left for the IAP ROM routines) |
| Stack | 1024 bytes (256 was too small: the `finalize_config` call chain needs about 540 bytes, see [LPC1115-finalize-hardfault.md](LPC1115-finalize-hardfault.md)) |
| Scheduler timer | CT32B1 (do not use for anything else) |
| Host serial | UART0 on PIO1_6 (RXD) / PIO1_7 (TXD), 250000 baud |
| Watchdog | WDT, 0.5 s timeout |

## Pin names and GPIO

Pins are named `PIOp_n` (for example `PIO2_10`):

| Port | Pins |
|---|---|
| 0 | `PIO0_0` ... `PIO0_11` |
| 1 | `PIO1_0` ... `PIO1_11` |
| 2 | `PIO2_0` ... `PIO2_11` |
| 3 | `PIO3_0` ... `PIO3_5` |

Which pins exist depends on the package; the firmware does not know which
ones are bonded out. `PIO1_6` and `PIO1_7` are reserved for the serial
connection. Inverted pins use the normal Klipper `!` prefix, pull-ups `^`
and pull-downs `~`.

Notes:

* Output writes use the LPC11xx masked-access data register, so each write
  is a single store.
* Toggling reads the pad level (the LPC11xx has no output-latch readback).
* The debug and reset pads power up in their special function. Using them
  as GPIO switches that function off:
  * `PIO0_0` is RESET.
  * `PIO0_10` is SWCLK and `PIO1_3` is SWDIO, so using them as GPIO,
    ADC (AD4) or SPI clock disables SWD.
  * `PIO0_11`, `PIO1_0`, `PIO1_1`, `PIO1_2` power up in a reserved function
    (they are ADC-capable pads, set to digital mode when used as GPIO).
* `PIO0_4` and `PIO0_5` are the I2C pads. They have no pull-ups and as GPIO
  they are open drain (they can only drive low).
* Pins on the analog-capable pads are set to digital mode automatically
  when used as GPIO.

## ADC

* 8 channels, 10-bit. `ADC_MAX` is 1023. Klipper scales this itself.
* Conversion clock 4 MHz (12 MHz / 3). Conversions are started in software
  and polled; no interrupts are used.
* Pin to channel mapping:

| Pin | Channel | Notes |
|---|---|---|
| `PIO0_11` | AD0 | |
| `PIO1_0` | AD1 | |
| `PIO1_1` | AD2 | |
| `PIO1_2` | AD3 | |
| `PIO1_3` | AD4 | shares the SWDIO pad |
| `PIO1_4` | AD5 | |
| `PIO1_10` | AD6 | |
| `PIO1_11` | AD7 | |

* The ADC is powered up and clocked the first time an ADC pin is
  configured.
* Only one conversion runs at a time; other channels wait their turn.

## Hardware PWM

* `PWM_MAX` is 255 (8-bit duty).
* Timers CT16B0, CT16B1 and CT32B0 are available. CT32B1 is reserved for
  the scheduler. Each timer has a single cycle time, so all PWM pins on one
  timer must use the same `cycle_time`; a different value shuts down with
  "PWM already programmed at different speed".
* The shortest possible cycle is 255 timer ticks (about 21 us at 12 MHz,
  roughly 47 kHz). The cycle time is rounded to the nearest multiple of 255
  ticks. A 16-bit timer can reach cycles of about 1.4 s.
* Pins:

| Timer | Match 0 | Match 1 | Match 2 |
|---|---|---|---|
| CT16B0 | `PIO0_8`, `PIO3_0` | `PIO0_9`, `PIO3_1` | `PIO3_2` |
| CT16B1 | `PIO1_9` | `PIO1_10`, `PIO2_4` | none |
| CT32B0 | `PIO2_5` | `PIO2_6` | `PIO0_1`, `PIO2_7` |

* Deliberately not offered: `PIO0_10` (SWCLK pad) and `PIO1_6`/`PIO1_7`
  (serial). Match 3 of each timer sets the cycle and cannot be an output.
* Match value 0 is 0% duty, 255 is 100%.
* Not verified: whether a duty change is applied immediately or at the
  next cycle. If it is applied immediately, a change can glitch one cycle.
* Software PWM through plain GPIO also works with `pwm: True` and
  `hardware_pwm: False`.

## SPI

* The two SSP controllers run as SPI masters with 8-bit frames, modes 0-3.
* Bit rate is 12 MHz / (CPSR x (SCR + 1)), up to 6 MHz. The firmware rounds
  the divider up, so the requested rate is never exceeded.
* The chip select is always a normal GPIO that the host drives.
* Bus names and pins (MISO, MOSI, SCK):

| Bus | MISO | MOSI | SCK |
|---|---|---|---|
| `ssp0` | `PIO0_8` | `PIO0_9` | `PIO0_6` |
| `ssp0a` | `PIO0_8` | `PIO0_9` | `PIO2_11` |
| `ssp0b` | `PIO0_8` | `PIO0_9` | `PIO0_10` (SWCLK pad) |
| `ssp1` | `PIO2_2` | `PIO2_3` | `PIO2_1` |

* `ssp0`, `ssp0a` and `ssp0b` are the same controller with a different SCK
  pad (selected through the `SCK0_LOC` register). Only one of them can be
  used at a time; a second one shuts down with "SSP already in use with
  different pins".
* The alternate SSP1 pads (`PIO3_2` SCK, `PIO1_10` MISO, `PIO1_9` MOSI) are
  not implemented because the location register encoding was not verified.

## I2C

* One controller, bus name `i2c0`: SCL on `PIO0_4`, SDA on `PIO0_5`. The
  pads are true open drain; external pull-ups are required.
* Polled master mode with repeated-start register reads.
* Error reporting: address NACK on write (`START NACK`), address NACK on
  read (`START READ NACK`), data NACK (`NACK`) and bus timeouts
  (`Timeout`). On a timeout the bus is released with a stop condition and
  the controller is restarted if it is stuck.
* Bus speed is applied per device at the start of each transfer: up to
  100 kHz uses an equal low/high split, above that a 2:1 low:high split
  (fast mode). The maximum is 400 kHz.
* Transfer timeouts scale with the length of the transfer.

## Reset and watchdog

* `FIRMWARE_RESTART` and `RESTART` use the generic Cortex-M reset command,
  which performs a software system reset. There is no bootloader on this
  port.
* The watchdog starts at boot and cannot be stopped until the next reset.
  It runs from the 12 MHz internal oscillator (independent of the main
  clock) with a 0.5 s timeout. A scheduler task feeds it every 50 ms, so a
  hung MCU resets itself.
* Attaching an SWD debugger and halting the core may trigger a watchdog
  reset. For long halts use a build without `watchdog.c`.
* The reset cause is readable with the firmware's own debug commands:
  `DUMP 0x40048030 1 32` in `klippy/console.py` reads `SYSRSTSTAT`
  (bit 2 = watchdog, bit 3 = brown-out). The bits are sticky across resets, so
  the value is cumulative since power-up; clearing it by `debug_write` did not
  work in testing.

## Example printer.cfg snippets

These show the syntax for the pins documented above. The pins are examples;
choose pins that exist on your board.

Basic connection and blink:

    [mcu]
    serial: /dev/ttyUSB0
    baud: 250000

    [printer]
    kinematics: none
    max_velocity: 100
    max_accel: 100

    [output_pin led]
    pin: PIO2_10

    [delayed_gcode blink]
    initial_duration: 1.0
    gcode:
      {% if printer['output_pin led'].value %}
        SET_PIN PIN=led VALUE=0
      {% else %}
        SET_PIN PIN=led VALUE=1
      {% endif %}
      UPDATE_DELAYED_GCODE ID=blink DURATION=0.5

Hardware PWM (25 kHz):

    [output_pin fan]
    pin: PIO2_5
    pwm: True
    hardware_pwm: True
    cycle_time: 0.00004
    value: 0

Analog input (thermistor on AD1):

    [temperature_sensor ntc]
    sensor_type: Generic 3950
    sensor_pin: PIO1_0
    pullup_resistor: 4700

SPI device on `ssp0`:

    [adxl345]
    cs_pin: PIO0_2
    spi_bus: ssp0

I2C device:

    [mpu9250 accel]
    i2c_bus: i2c0

## Limitations and open questions

* Clock is 12 MHz. The chip can run at 48-50 MHz with the PLL. Faster clocks
  need the PLL set up in `main.c` and every derived divisor rechecked (UART
  baud, ADC, SSP, I2C).
* Flash use is 42 KB of 64 KB because the default-on optional Klipper
  features (NeoPixel, TMC UART, ST7920, HD44780, HX71x, CS1237, pulse
  counter, buttons, trigger analog, plus the ADC/SPI/I2C/PWM drivers) are
  all enabled. Disable unused ones in `menuconfig` if you need space.
* `RAM_SIZE` reserves the top 32 bytes for the IAP routines; this reserve
  has not been checked against UM10398.
* There is no `udelay()` and no bootloader-request support.
* Only the single I2C controller and two SSP controllers exist on this
  chip. UART1-style extra serial ports are not implemented.
* No part of the port has been measured for scheduler jitter or free
  dynamic memory under a realistic configuration.
* The stack sits directly above the dynamic memory that `finalize_config`
  fills with the move queue and zeroes (`alloc_chunk` memset). Any stack use
  beyond `STACK_SIZE` is therefore silently corrupted after finalize. Peak
  stack depth has been observed only on the `finalize_config` path (536
  bytes); a static call-graph estimate puts the worst case at about 828 bytes
  against the 1024-byte stack. There is no overflow detection yet. Consider a build-time stack-usage check or
  painting the stack at boot and reporting the high-water mark.

## Suggested hardware test order

1. Identify over UART, then run the blink demo.
2. `FIRMWARE_RESTART` and `RESTART`: the MCU should come back and reconnect.
   Then, in the console, `allocate_oids`, `config_digital_out` and
   `finalize_config`: the MCU must keep answering `get_uptime` (this is the
   regression test for the stack-size bug).
3. Run for several minutes: the watchdog should stay silent. An unexpected
   reset suggests the 0.5 s timeout is too short.
4. ADC on a known voltage divider (compare against a multimeter).
5. PWM on an LED or oscilloscope, including 0% and 100% and a duty change
   while running.
6. SPI with MISO wired to MOSI (loopback) at a few rates.
7. I2C against any known device, including a deliberate wrong address to
   check that the NACK is reported.

## Register and pin references

The pin function tables come from the `lpc11xx` Rust PAC documentation
(docs.rs, pad names list the functions in numeric order, and reserved
functions are omitted from the label), cross-checked against the CMSIS
`LPC11xx.h` register layouts and the NXP LPC11xx driver conventions.
IOCON register offsets, IRQ numbers and peripheral base addresses were
checked against the CMSIS header. The official reference is UM10398
(LPC111x/LPC11Cxx user manual).
